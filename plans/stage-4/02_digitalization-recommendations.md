# Рекомендации по цифровизации агрообразования (Этап 4)

> Для ПРООН и вузов-партнёров — обобщение опыта построения платформы FOLUR Казахстан.

## 1. Архитектурные принципы, подтверждённые проектом

1. **Статическая платформа вместо LMS.** GitHub Pages + Colab + Zenodo дают $0/мес и нулевое администрирование; система переживает окончание финансирования. LMS оправдана только там, где уже есть штат её сопровождения (вузовский Moodle — как дополнение, не замена).
2. **Контент как код.** Markdown + git: рецензирование через pull request, журнал доработок = история коммитов, автоматическая валидация качества (`validate_content.py`, strict-сборка) перед каждой публикацией. Это дешевле и надёжнее «документов по папкам».
3. **Оценивание с индивидуальными вариантами** — обязательный минимум достоверности: детерминированная генерация варианта по ID слушателя + pre/post-срезы + два следа учёта (бумажный лист + верифицируемый код результата).
4. **Данные по уровням доступа.** Трёхуровневая политика (обезличенное открыто / производные открыто / полное — по разрешению) снимает конфликт «открытость vs законодательство о пространственных данных». Обезличивание в локальную СК сохраняет 100% учебной ценности.
5. **ИИ как рабочий инструмент, не тема.** Сквозной ИИ-слой (no/low/pro-code) с инвариантом «ИИ ускоряет — человек верифицирует» готовит к реальной практике GeoAI; вендор-независимость обязательна.

## 2. Рекомендуемые следующие шаги цифровизации (за рамками контракта)

| Шаг | Эффект | Оценка усилий |
|---|---|---|
| Open Badges / криптоподписанные сертификаты | верифицируемость без реестра | средняя (нужен issuer-процесс) |
| LLM-генерация вариантов заданий (по методологии заявки) | вариативность выше детерминированной подвыборки | средняя; требует бюджета на API или локальной модели |
| Казахская локализация ядра (П1–П3) | доступность для казахскоязычных МСБ | высокая (перевод + вычитка) |
| Автогрейдинг ноутбуков (nbgrader/CI) | масштабирование практикумов без тренеров | средняя |
| Аналитика использования (GoatCounter/Plausible) | данные для KPI устойчивости | низкая |

## 3. Антирекомендации (проверено на бенчмарке аналогов и опыте проекта)

- Не публиковать тяжёлые ассеты (слайды 70–90 МБ) — сельский интернет их не тянет; PDF ≤3 МБ на модуль.
- Не полагаться на Google Forms для оценивания — тривиально обходится, не измеряет прирост.
- Не привязываться к одному ИИ-вендору и не делать ИИ условием прохождения.
- Не смешивать в одном репозитории публичный контент и чувствительные данные: раздельные контуры с самого начала (у нас: публичная платформа отдельно от тендерных документов и сырых координат).
