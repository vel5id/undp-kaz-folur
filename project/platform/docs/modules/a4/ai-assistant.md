# ИИ-ассистент в работе: пакетная фильтрация промеров под контролем человека

!!! tip "Впервые работаете с этими программами?"
    Где скачать, как установить и что нажать при первом запуске — в справке [«Программы и сервисы»](../../software.md): [Google Colab](../../software.md#colab). Встроенный редактор Python установки не требует.

> Модуль **А4: Водные ресурсы, климатическая адаптация и батиметрия** · Уровень: **Pro-code** (студент, инженер)
> Инструменты: **Claude Code / OpenCode** — терминальные кодинг-агенты (взаимозаменяемы; вендор-независимость — принцип платформы, см. [рамку ИИ-слоя](../../ai-tools.md)).
> Время: ~45–60 мин. **Задание выполнимо и полностью без ИИ** — тогда вы пишете конвейер сами по [практикуму](practicum/01-karta-glubin-i-ndwi.md); ИИ-слой ускоряет, но не является условием прохождения.

!!! warning "Главное правило: ИИ ускоряет — человек верифицирует"
    Кодинг-агент пишет геопайплайн за минуты. Но ответственность за результат — на вас: сгенерированный код проходит ваше ревью, а результат — независимую проверку по опорным глубинам. Результат ИИ без верификации — не результат.

## Цель задания

Освоить производственный цикл работы с кодинг-агентом на реальной задаче модуля: **постановка задачи агенту → ревью сгенерированного кода → независимая верификация результата**. Предметная задача — CLI-утилита пакетной фильтрации сырых эхолотных промеров (лекция 2, §3) с протоколом чистки и контролем по опорным глубинам.

## Что понадобится

- Терминал с установленным Claude Code **или** OpenCode (любой из них; далее — «агент»).
- Python 3 с pandas, NumPy, SciPy.
- <code>datasets/bathymetry-training-80k.csv</code> (уровень A: локальная СК, <code>point_id, x_m, y_m, depth_m</code>; политика данных — [Датасеты](../../datasets.md)).
- Пройденная [лекция 2](lectures/02-karta-glubin-iz-promerov.md) — без неё вы не сможете судить о правильности кода агента, и задание теряет смысл.

## Пошаговое задание

### Шаг 1. Подготовьте опорные глубины ДО запуска агента

Верификацию готовят до генерации кода — чтобы проверка не подстраивалась под результат. Напишите **самостоятельно** (это 10 строк) скрипт <code>make_reference.py</code>: случайно выберите 500 точек с <code>depth_m > 0</code>, сохраните их <code>point_id</code> в <code>reference-ids.csv</code>. Эти точки — ваши «опорные глубины»: заведомо доброкачественный контрольный набор, судьбу которого в фильтре агента вы проверите на шаге 4. Зафиксируйте seed генератора случайных чисел — проверка должна быть воспроизводимой.

### Шаг 2. Поставьте задачу агенту

Сформулируйте техническое задание на естественном языке. Рабочий стартовый промпт (адаптируйте под себя):

```text
Напиши CLI-утилиту filter_bathymetry.py на Python (pandas, scipy).
Вход: CSV с колонками point_id,x_m,y_m,depth_m. Выход: очищенный CSV
(исходный файл не изменять) и JSON-протокол чистки.
Фильтры по уровням, каждый включается/настраивается аргументами CLI:
1) физический диапазон: --min-depth 0 --max-depth <значение>;
2) изолированные нули: ноль удаляется, если медиана k ближайших
   соседей больше --zero-tol (по умолчанию 1.0 м), k = --neighbors 12;
3) локальные выбросы: |depth - медиана соседей| > --outlier-tol.
Протокол: сколько точек удалил каждый фильтр, параметры запуска.
Ограничение: до 1 млн точек, поиск соседей — cKDTree, без циклов по строкам.
Добавь --dry-run (только протокол, без записи) и unit-тесты на синтетике.
```

Обратите внимание: вы диктуете агенту **архитектуру решения из лекции 2**, а не просите «почисть данные как-нибудь». Качество постановки — половина результата: агент, получивший размытую задачу, примет решения за вас, и вы о них не узнаете.

### Шаг 3. Ревью сгенерированного кода (обязательный, не пропускается)

Прочитайте код агента целиком, как чужой pull request. Контрольный список ревью — типовые ошибки, которые кодинг-агенты допускают в геозадачах:

- [ ] **Сосед номер ноль.** При запросе k соседей через KD-дерево первым соседом точки является она сама. Если агент не исключил её, медиана соседей «подтянута» к самой точке — фильтр выбросов ослаблен. Это самая частая ошибка в подобном коде.
- [ ] **Порядок фильтров.** Выбросы должны оцениваться после исключения нулей из статистики соседей (или устойчиво к ним) — иначе нули утягивают медиану вниз на мелководье.
- [ ] **Перезапись входа.** Убедитесь, что исходный CSV не модифицируется ни при каких аргументах.
- [ ] **Жёстко зашитые константы** вместо CLI-аргументов; молчаливые допущения о разделителе/кодировке CSV.
- [ ] **Осмысленность тестов.** Агенты любят тесты, которые проверяют, что код «не падает», а не что он прав. Тест должен подсовывать синтетический выброс и проверять, что удалён именно он.

Найденные проблемы возвращайте агенту текстом («первый сосед — сама точка, исключи её из медианы») и просматривайте диф исправления. Ни одна строка не должна остаться непонятой: «работает, но не знаю почему» — дисквалифицирующее состояние для инженера.

### Шаг 4. Независимая верификация результата (ядро задания)

Запустите утилиту на учебном датасете и проверьте результат **своим** кодом, не написанным агентом:

1. **Контроль по опорным глубинам.** Пересеките <code>point_id</code> удалённых точек со своим <code>reference-ids.csv</code> из шага 1. Опорные точки — случайная выборка нормальных промеров; доля удалённых среди них должна быть близка к общей доле статистически удалённых точек (порядка процента). Если фильтр съел заметно больше опорных точек — он удаляет нормальные данные; разбирайтесь, прежде чем двигаться дальше.
2. **Сверка статистик.** До/после: количество точек, min/max/медиана глубин, диапазон координат. Максимум 16,1 м должен пережить чистку (это реальная глубина, лекция 2 §3.1); медиана не должна сместиться заметно.
3. **Карта удалённого.** Постройте scatter удалённых точек: рассеяны — хорошо; связные структуры — фильтр стирает морфологию дна.
4. **Протокол против факта.** Числа в JSON-протоколе утилиты должны сходиться с вашим независимым пересчётом (например, <code>wc -l</code> входа/выхода).

### Шаг 5. Стресс-тест постановкой

Финальный приём профессиональной работы с агентами — проверка на устойчивость к параметрам: запустите утилиту с <code>--outlier-tol</code> вдвое меньше и вдвое больше базового. Доля удалённых точек должна меняться монотонно и объяснимо. Скачкообразное или парадоксальное поведение — признак ошибки, не пойманной на ревью.

## Критерии зачёта

| # | Критерий | Проверка |
|---|---|---|
| 1 | Утилита работает по спецификации: CLI-аргументы, «сырой файл неприкосновенен», JSON-протокол | запуск + <code>--dry-run</code> |
| 2 | Проведено ревью: слушатель называет ≥2 найденных (или осознанно проверенных) риска из чек-листа шага 3 и показывает, как убедился | устный/письменный разбор |
| 3 | Верификация по опорным глубинам выполнена кодом слушателя, написанным до генерации; выводы сформулированы числами | <code>reference-ids.csv</code> + скрипт проверки |
| 4 | Статистики до/после и карта удалённого приложены и проинтерпретированы | артефакты |
| 5 | Слушатель может объяснить любую строку итогового кода | выборочные вопросы |

Не зачитывается: работа, где верификация сгенерирована тем же агентом, что и утилита; работа без ревью («агент написал — я запустил»); утверждения о качестве чистки без чисел.

## Если агент недоступен

Выполните то же задание без ИИ: напишите утилиту сами по спецификации шага 2 (основа уже есть в [практикуме](practicum/01-karta-glubin-i-ndwi.md)), а шаги 1, 4, 5 выполняются без изменений — верификация обязательна при любом происхождении кода. Именно в этом главный урок задания: **процедура проверки не зависит от того, кто написал код — человек или ИИ.**
